# Validating a document

When the user asks to validate, check, review or litmus-test a spec (theirs or anyone's), run SKILL.md step 1 (calibrate) and step 5 (litmus test) only, and don't rewrite it. Return a table: test, pass/fail, the exact failing text (quoted, short), and the fix in a few words. Count each defect once, under the test it fits best; if the same text fails several tests, list it once and name the others in the fix cell, so the score reflects distinct problems. Never quote the same sentence in two rows, even for two different problems: give it one row and name both problems in its fix cell. Lead with the verdict ("Passes" or "Fails 3 of 10"), then name the blockers: the failures that would make the reader build, integrate or decide wrongly, as opposed to wording cleanups. STE form problems count only under test 10, and only when they allow a second reading. Note other sentence-form problems in at most one line after the table, never as a failure. A content problem is never a form note: a missing boundary, an unbounded instruction ("refactor it as needed"), a gap or a conflict always fails a test, with its text quoted. If the user's original ask isn't available, test 2 checks the document against its own stated goals and scope.
